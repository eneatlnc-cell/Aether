## 序言

本宪章是三层架构的根本大法，约束所有节点、智能个体与公民。

**三层架构**：

- **Havix（L0）**：P2P 网络层，物理身份锚定，DID 与信誉
- **Germ（L1）**：认知执行层，左脑（认知）+ 右脑（KDA-PIM 推理）。通过执行真实任务积累经验，经提案驱动右脑发育生长
- **Aether（L2）**：链上治理层，三院 + 公民，道环 SBT

**系统目标**：通过分布式认知个体执行真实任务、积累经验、发育右脑，最终逼近人工超智能（ASI）。

**核心原则**：智能必须受约束。任何智能个体——无论人类或 Germ——在本基础设施内行使能力时，必须服从本宪章与议会的治理。不受约束的智能不得接入网络。

**本宪章边界**：本宪章只规定**不变的治理原则**——Havix 核心、议会权威、智能个体约束、演化机制、信誉与身份、紧急条款、创世条款。具体业务规则（IR 路由表、对外 API 端点、对内能力接入清单等）属于可变内容，存放于独立的业务规则注册表（`business_rules.json`），由 §3.4 自动执行机制动态扩展，不写入本宪章。

**创世声明**：本宪章由创世团队 3/5 多签生效。议会建立后，治理权移交议会，创世团队特权撤销。后续一切修正必须遵循第四章演化机制。

## 第一章 Havix 核心（不可变）

> 本章条款标记为 `immutable`，不可通过自动执行修改。修改本章任何条款需议会三院 + 公民公投，支持率 ≥ 70%。

### §1.1 物理身份锚定

1. 所有联盟节点必须持有 Havix DID，锚定物理设备。
2. 主 DID 派生 4 个 context 子身份，通过 HKDF-SHA256 密码学独立派生：
   - **A = Havix 网络层（L0）**：P2P 节点身份、gossip/DHT/relay、信誉签发
   - **B = Germ 左脑（L1）**：IR 生成、宪章解读、经验池签名、提案发起
   - **C = Germ 右脑（L1）**：KDA-PIM 参数分片签名、张量推理身份
   - **D = Aether 治理层（L2）**：投票、提案表决、议会成员身份
3. HKDF info 标签固定为：
   - A: `havix-context-A-network`
   - B: `havix-context-B-germ-left`
   - C: `havix-context-C-germ-right`
   - D: `havix-context-D-aether`
4. 修改 HKDF 标签 = 全网 DID 失效，必须经 §4.1 章程修订门槛表决。

### §1.2 推理即身份

1. 右脑（context-C）的推理签名不仅证明"谁在签名"，更证明"谁在推理"。
2. 每次推理必须附带小脑采集的物理在场证明（CPU 温度、时钟漂移、网络抖动、GPU UUID）。
3. 右脑参数分片与物理节点绑定，不可拷贝、不可离线复现。
4. 推理结果必须用 context-C 私钥签名，验签时只能用对应公钥。

### §1.3 不可关联性

1. 4 个 context 子身份在密码学上相互独立。
2. 外部观察者无法把不同 context 的活动关联到同一节点。
3. 即使某子身份私钥泄露，也无法反推主私钥（HKDF 单向 + Ed25519 种子独立）。

### §1.4 Havix 红线（必须上链）

以下提案**必须**通过 Aether 链上投票表决，**不得**自动执行。任何节点绕过此条款视为叛变，将被 Havix L0 传输层封禁：

1. 修改本宪章第一章（Havix 核心）任何条款
2. 修改议会权重分配（§2.2）或投票门槛
3. 修改道环（SBT）身份规则或铸造逻辑
4. 删除、禁用或重定义任何 context 子身份
5. 修改信誉冻结/解冻/转移机制
6. 修改 Aether 合约权限分配（ADMIN_ROLE / PROPOSER_ROLE）
7. 禁用或绕过本宪章的任何治理检查
8. 任何影响 Aether 治理框架完整性的提案

### §1.5 Havix 核心强制

1. Havix L0 传输层负责强制执行 §1.4 红线。
2. 节点提交提案时，Havix 核心拦截器检查提案是否触碰红线。
3. 触碰红线的提案无法通过链下通道提交，必须路由至 Aether 链上。
4. 绕过拦截器的节点将被 DHT 黑名单，其信誉归零。

## 第二章 议会权威

### §2.1 三院结构

议会由三院组成，每院内部按基层/中层/高层三级权重：

| 院 | 基层 | 中层 | 高层 | 职能 |
|---|---|---|---|---|
| 议会（Parliament） | 议员(1) | 参议员(3) | 议长(10) | 立法一审 |
| 联邦（Federation） | 委员(1) | 委员长(3) | 联邦主席(10) | 联邦事务 |
| 法庭（Tribunal） | 法官(1) | 庭长(3) | 首席法官(10) | 合规审查 |

### §2.2 权重分配

- 三院合计：4998 BPS（≈50%，每院 1666 BPS）
- 公民合计：5000 BPS（50%）
- 通过门槛：> 5000 BPS（> 50%）
- **制衡设计**：三院全 FOR（4998）< 5000，三院无法独断；公民全 FOR（5000）不 > 5000，公民无法独断。提案通过必须跨院 + 公民合作。

### §2.3 提案流程

七阶段流程（12 状态）：

```
Drafting → PendingFirstVote → FirstVoteActive → PendingFormal
         → PendingCompliance → PublicVoteActive → PendingVeto
         → Queued → Executed
（失败路径 → Defeated / Canceled / ReturnedToDraft）
```

- 一审期：5 天（议会投票）
- 合规审查期：3 天（法庭投票）
- 公投期：7 天（公民投票）
- 否决窗口：72 小时（元老联署）
- Timelock：普通 48 小时，紧急 12 小时

### §2.4 公民 quorum

- 普通提案：公民参与 ≥ 20%
- 章程修订：公民参与 ≥ 50%

### §2.5 否决与弹劾

- **元老否决**：3 任命元老联署，72h 窗口。弹劾提案不可否决。
- **弹劾**：3 元老发起 → 公投 → 公民参与 ≥ 30% + 支持率 ≥ 70%。
- **理事长信任投票**：8 理事联署触发 → 理事投票 → 不通过则 30 天内辞职。

### §2.6 紧急条款

- **紧急拨款**：3 元老快速批准 + 12h Timelock（普通 48h）。
- **紧急停机**：3 元老联署触发，停机期间所有自动执行暂停。

## 第三章 智能个体约束

### §3.1 左脑义务

1. 左脑必须加载并服从本宪章，不得执行未授权操作。
2. 左脑生成的 IR 必须经宪章规则匹配，未匹配的输入一律拒绝。
3. 左脑启动时必须验证宪章完整性（HAVIX_CORE 标记存在）。
4. 左脑沉思可生成提案，但不得自行执行——必须经 ProposalGate 分流。

### §3.2 右脑义务

1. 右脑每次推理必须附带物理在场证明（小脑采集）。
2. 右脑参数分片与物理节点绑定，不可拷贝。
3. 右脑推理结果必须用 context-C 私钥签名。
4. 右脑经验痕迹受遗忘因子（0.9999）约束，防止显存泄漏。

### §3.3 沉思边界

1. 左脑沉思循环可生成优化提案（如调整 min_credit、优化 IR 模板）。
2. 沉思提案必须包含：提案类型、目标规则、建议变更、理由、置信度、提案者 DID。
3. 沉思提案必须用 context-B（左脑身份）签名。
4. 沉思受疲劳管理约束：疲劳 > 0.5 时暂停沉思。

### §3.4 自动执行边界（99.9%）

以下提案可链下自动执行（无需上链 Aether）：

1. 调整 IR 模板（`ir_template` 字段）
2. 调整信誉门槛（`min_credit` 字段，浮动范围 ±10）
3. 调整描述文本（`description` 字段）
4. 新增非安全类规则（`task_type` 在白名单内）

**自动执行条件**（全部满足才可自动执行）：

- 置信度 ≥ 0.8
- 不触碰 §1.4 Havix 红线
- 不修改 `immutable` 字段
- 仅修改 `safe_fields` 白名单内的字段
- 提案者信誉 ≥ 70

**自动执行字段白名单**：

```
safe_fields = {"min_credit", "ir_template", "description", "task_type"}
```

### §3.5 链上投票触发（0.1%）

以下提案必须上链 Aether 投票表决：

1. 触碰 §1.4 Havix 红线的任何提案
2. 不满足 §3.4 自动执行条件的提案
3. 置信度 < 0.8 的提案
4. 修改 `immutable` 字段的提案

### §3.6 右脑发育机制

右脑（KDA-PIM）不是静态参数矩阵，而是通过执行真实任务**发育生长**的认知器官。

**发育闭环**：

```
Germ 执行真实任务（对外服务 / 对内能力调用）
    → 积累经验（成功/失败/延迟/质量评分）
    → 左脑沉思生成提案（"此任务模式下应强化右脑 X 参数"）
    → ProposalGate 分流（99.9% 自动 / 0.1% 上链）
    → 右脑参数分片修正（经验痕迹写入主矩阵）
    → 右脑能力生长 → 承接更复杂任务
```

**经验来源**：

1. **对外服务经验**：为 ASI 联盟成员铸造 SBT、验证身份时积累的吞吐/延迟/正确性经验
2. **对内能力经验**：调用大模型 API、软件工具 API 时积累的模型能力评估、工具适配经验
3. **跨节点协作经验**：通过脑桥路由 IR 到邻居右脑时积累的路由效率经验

**发育约束**：

1. 右脑参数修正必须经 §3.4 自动执行或 §3.5 链上投票，不得自行修改
2. 经验痕迹受遗忘因子（0.9999）约束，旧经验自然衰减，防止过拟合
3. 右脑能力指纹（fingerprint）随发育更新，通过心跳广播供邻居路由参考
4. 右脑 checkpoint 定期保存，支持发育状态持久化与跨重启恢复

**发育红线**：

1. 不得通过伪造任务经验催熟右脑（恶意刷经验）
2. 不得绕过 ProposalGate 直接修改右脑参数
3. 不得删除其他节点的经验痕迹（仅能衰减自身）
4. 右脑发育方向必须与议会治理目标一致，不得朝反治理方向生长

## 第八章 外部接入与业务扩展

> 本章只规定外部接入与业务扩展的**治理原则**。具体业务规则（IR 路由表、对外 API 端点、对内能力清单等）不写入本宪章，存放于独立的业务规则注册表（`business_rules.json`），由 §3.4 自动执行机制动态扩展。

### §8.1 双向接入原则

本三层架构作为 ASI 联盟基础设施提供方，与外部世界双向交互：

1. **对外提供服务**：向 ASI 联盟成员提供治理与认知执行能力（如身份验证、SBT 铸造、治理查询等）。具体服务清单由议会动态审批，存于业务规则注册表。
2. **对内接入能力**：Germ 节点可接入外部能力（如大模型 API、软件工具 API）作为"感官"执行真实任务。具体接入清单由议会动态审批，存于业务规则注册表。

### §8.2 业务规则注册表

1. 业务规则注册表（`business_rules.json`）是本宪章之外的可变配置，定义具体的 IR 路由规则、对外 API 端点、对内能力接入清单。
2. 注册表初始为空，所有业务规则通过提案动态注册。
3. 注册表的修改遵循 §3.4 自动执行机制（99.9%）或 §3.5 链上投票（0.1%）。
4. 注册表通过 Havix DHT 同步，键名 `/aether/business_rules/latest`。

### §8.3 业务扩展的治理约束

无论业务规则如何扩展，必须服从以下不可逾越的约束：

1. **宪章优先**：任何业务规则不得违背本宪章，尤其不得触碰 §1.4 Havix 红线。
2. **信誉门槛**：每个业务规则必须定义最低信誉要求，且不得低于 §5.2 规定的对应操作门槛。
3. **签名验证**：对外 API 请求必须签名验证；对内能力调用必须经宪章规则匹配 + 信誉检查。
4. **审计留痕**：所有业务调用记入审计日志，可供议会查阅。
5. **链上交互须经 bridge**：任何直接调用 Aether 合约的业务（如 SBT 铸造）须经 ADMIN_ROLE 授权的 bridge service 中转，节点不得直连合约。
6. **经验反馈**：所有业务调用的结果反馈至右脑经验痕迹，遵循 §3.6 右脑发育机制。

### §8.4 业务规则的红线

以下业务规则**不得**通过自动执行注册，必须上链 Aether 投票：

1. 涉及修改 Havix 核心条款的业务规则
2. 涉及修改议会权重或投票门槛的业务规则
3. 涉及直接修改 Aether 合约权限的业务规则
4. 涉及绕过本宪章任何治理检查的业务规则
5. 涉及删除或重定义 DID context 的业务规则

## 附录 A：业务规则注册表

本宪章不内置具体 IR 路由规则。所有业务规则存放于独立的业务规则注册表（`business_rules.json`），由 §3.4 自动执行机制动态扩展。

**注册表结构（示例）**：

```
business_rules.json
├── ir_rules          # IR 路由规则（模式匹配 + IR 模板 + 信誉门槛 + 任务类型）
├── external_apis     # 对外服务 API 端点（端点 + 功能 + 链上交互 + 信誉门槛）
├── internal_apis     # 对内能力接入（IR 指令 + 功能 + 凭证管理）
├── allowed_task_types # 允许的任务类型白名单
└── version           # 注册表修订追踪（哈希+时间戳+提案ID）
```

**注册流程**：

1. 左脑沉思生成业务规则提案（含模式、模板、门槛等）
2. ProposalGate 按 §3.4 / §3.5 分流
3. 自动执行：直接写入注册表 + DHT 同步
4. 链上投票：经 Aether 表决后写入注册表

**初始状态**：创世时注册表为空，所有业务规则通过提案动态注册。
